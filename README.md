# سالن زیبایی کیمیا | Kimia Beauty & Atelier

وب‌سایت فارسی راست‌به‌چپ سالن زیبایی کیمیا با معرفی آتلیهٔ عکاسی، خدمات، درخواست نوبت، ساعت کاری و نشانی. نسخهٔ میزبانی‌شده از یک Cloudflare Worker استفاده می‌کند تا صفحه و API درخواست نوبت روی همان دامنه باشند.

## پایگاه داده

طرح PostgreSQL با هدف اجرای روی Supabase در `db/migrations/001_initial_schema.sql` قرار دارد. طرح شامل دسته‌بندی و خدمات، اعضای تیم، ساعت کاری، درخواست‌های نوبت، نوبت‌های تأییدشده، گالری و محدودسازی درخواست‌هاست. جدول درخواست‌ها برای دسترسی مستقیم عمومی بسته است؛ فرم وب فقط از RPC محدود `create_booking_request` استفاده می‌کند. اطلاعات قیمت در این نسخه ذخیره یا نمایش داده نمی‌شوند.

کد Worker از API سازگار با PostgREST/Supabase استفاده می‌کند. Supabase یک پایگاه PostgreSQL مدیریت‌شده و Data API روی HTTP می‌دهد؛ Worker این Sites اتصال TCP مستقیم به PostgreSQL ندارد. برای فعال‌سازی واقعی باید Migration اجرا و این متغیرهای محرمانه در تنظیمات Sites ثبت شوند:

- `SUPABASE_URL`: آدرس پروژه
- `SUPABASE_SECRET_KEY`: کلید محرمانهٔ سمت سرور؛ در مرورگر یا سورس قرار نگیرد
- `RATE_LIMIT_SALT`: رشتهٔ تصادفی محرمانه برای هش‌کردن IP پیش از ثبت محدودیت درخواست

تا وقتی این موارد ثبت نشده‌اند، صفحه کار می‌کند اما API درخواست نوبت پاسخ «در حال راه‌اندازی» می‌دهد و اطلاعات مشتری ذخیره نمی‌شوند. برای فعال‌سازی:

1. پروژهٔ Supabase بساز یا مشخصات PostgreSQL موجودت را اعلام کن.
2. فایل Migration را در SQL Editor دیتابیس اجرا کن.
3. URL پروژه و کلید Secret را در Environment Variables سایت تنظیم کن؛ کلید Secret را داخل کد یا چت عمومی قرار نده.
4. نسخهٔ Worker را دوباره Deploy کن و یک درخواست آزمایشی ثبت کن.

اگر PostgreSQL روی VPS خودت باشد، به‌جای Supabase Data API باید یک API سرویس جداگانه روی VPS با دسترسی محدود به دیتابیس داشته باشیم؛ Worker نباید مستقیماً به پورت PostgreSQL عمومی وصل شود.

## توسعه و بررسی محلی

```bash
bash scripts/build.sh
node scripts/validate-artifact.mjs
node scripts/test-worker.mjs
```

`src/index.html` صفحهٔ اصلی، `src/assets/` تصاویر پیش‌نمایش طراحی، `worker/index.template.js` مسیرهای Worker و `db/migrations/` نسخه‌بندی SQL را نگه می‌دارند. تصاویر فعلی برای نمایش کانسپت تولید شده‌اند و باید با عکس‌های واقعی مجموعه جایگزین شوند.

## محدودهٔ نسخهٔ فعلی

فرم عمومی فقط درخواست نوبت را ثبت می‌کند؛ هیچ زمان خالی به‌صورت خودکار رزرو نمی‌شود. تبدیل درخواست به `appointment` و مدیریت خدمات/گالری از پنل مدیر در فاز بعد انجام می‌شود. جدول‌ها برای این مسیر آماده‌اند اما پنل مدیریت عمومی وجود ندارد.

## تجربهٔ درخواست نوبت

کارت‌های خدمات، انتخاب را به فرم سه‌مرحله‌ای منتقل می‌کنند: انتخاب خدمت و روز/ساعت پیشنهادی، اطلاعات تماس، سپس مرور درخواست و رضایت تماس. تقویم بومی مرورگر استفاده می‌شود و تاریخ در مرور نهایی به فارسی نمایش داده می‌شود. جمعه و روزهای گذشته در رابط رد می‌شوند؛ زمان انتخابی وعدهٔ ظرفیت خالی نیست. وضعیت ثبت از `/api/health` خوانده می‌شود؛ تا راه‌اندازی دیتابیس، مرحلهٔ آخر تماس تلفنی پیشنهاد می‌کند و درخواست ارسال نمی‌شود. اطلاعات فرم در localStorage ذخیره نمی‌شود.

گالری فعلی شامل تصاویر مفهومی با بزرگ‌نمایی است. راهنمای مراجعه، پرسش‌های متداول و نوار تماس/نوبت موبایل اضافه شده‌اند. بررسی دیداری مرورگر در این محیط انجام نشده؛ پیش از پذیرش نهایی، نمای موبایل و تقویم بومی روی دستگاه‌های واقعی بررسی شود.
